# AI Finance Platform 问题整改文档

## 1. 文档目的

本文档用于沉淀本次并行分析发现的系统问题，说明问题影响、根因判断、整改方向、优先级和验收标准，作为后续整改执行和验收的统一依据。

适用范围：

- 后端：Spring Boot 3.4.5 + Java 21 + JPA + Redis + Spring AI
- 前端：Vue 3 + Vite + TypeScript + Vitest
- 运行环境：Docker Compose 本地开发、Caddy 反向代理生产部署

## 2. 分析方法

本次分析采用多视角并行方式，尽量避免单一视角误判：

- 架构视角：看分层、边界、扩展性和长期可维护性
- 工程视角：看构建、测试、依赖一致性和交付稳定性
- 产品视角：看用户路径、功能正确性和体验闭环
- 运维视角：看可观测性、部署安全、运行稳定性和配置治理
- QA 视角：看回归风险、契约漂移和测试可信度

## 3. 当前系统基线

### 3.1 已确认的技术现状

- 后端使用 Spring Boot、Spring Data JPA、Spring AI、MySQL、Redis
- 前端使用 Vue 3、Vite、TypeScript、Axios、ECharts、Vitest
- 本地环境通过 `docker-compose.yml` 提供 `mysql`、`redis`、`backend-dev`、`frontend-dev`
- 生产环境通过 `docker-compose.prod.yml` 提供 `mysql`、`redis`、`backend`、`frontend`、`caddy`

### 3.2 当前成熟度判断

当前仓库已经不是纯原型，具备比较完整的 MVP 形态，但距离“公司主流使用系统”仍有明显差距，主要体现在：

- 构建与依赖完整性不稳定
- 前后端契约已经发生漂移
- 安全、校验、异常治理不足
- 可观测性与运维安全不足
- 异步执行策略不具备生产级约束
- 导航、配置、用户路径仍有明显破口

## 4. 核心问题总览

### 4.1 P0 级问题

#### P0-1 前端构建链路不稳定

问题描述：

- 当前前端 `npm run build` 会因为 `lucide-vue-next` 无法正确解析而失败
- 相关组件已经依赖该包，但实际安装状态、锁文件和声明状态未完全对齐

影响：

- 项目无法稳定打包交付
- 团队成员与 CI 环境可能出现不一致结果
- 后续前端迭代建立在不稳定基础上

根因判断：

- `package.json`、`package-lock.json` 和实际依赖安装状态没有完全收敛
- 仓库缺少“干净环境可重建”的强约束验证

整改方向：

- 对齐 `package.json`、`package-lock.json` 与实际安装结果
- 确保在干净机器上可以直接执行 `npm ci` 和 `npm run build`
- 将前端依赖完整性检查纳入 CI

验收标准：

- 干净环境下 `npm ci` 成功
- 干净环境下 `npm run build` 成功
- Vue SFC 编译阶段不存在模块缺失错误

#### P0-2 AI 功能前后契约已漂移

问题描述：

- 前端 `api/ai.ts` 仍保留同步 `askAi()` 能力
- `AiAnalysisView.vue` 和 `AiAssistantFloating.vue` 已直接改为原生 `fetch` 串流
- 测试仍然 mock `askAi()`，与真实运行路径脱节

影响：

- 测试已经失去可信度
- AI 功能后续迭代难以安全推进
- 视图层开始承担传输协议解析，导致重复实现和维护成本上升

根因判断：

- 引入串流能力时没有统一前端 AI 客户端边界
- 页面组件直接接管了传输层逻辑

整改方向：

- 定义统一 AI 客户端契约，覆盖同步与串流两种能力
- 将 SSE/流式解析逻辑下沉到共享 service 或 composable
- 让测试围绕共享客户端而不是页面实现细节进行 mock

验收标准：

- AI 同步与串流能力都统一走共享客户端
- 页面层不再直接解析传输协议
- AI 相关测试与真实运行行为一致

#### P0-3 AI 问答仍使用硬编码 `periodId`

问题描述：

- AI 问答链路里仍存在固定 `periodId = 4`
- 页面选择的财务期间没有被统一传播到 AI 分析、浮窗助手和报告生成场景

影响：

- 用户可能看到错误期间的 AI 分析结果
- AI 结论可能与当前驾驶舱展示数据不一致
- 这是直接的业务正确性问题

根因判断：

- 缺少统一的当前期间状态源
- 各页面采用本地假设而不是共享状态

整改方向：

- 建立统一的当前期间状态源
- 让 AI、报告、预算偏差等模块共享所选期间
- 去除所有用户面向逻辑中的硬编码期间值

验收标准：

- 所有 AI 与报告请求都使用当前用户选中的期间
- 切换期间后，依赖模块结果同步更新
- 生产代码中不再存在硬编码业务期间值

### 4.2 P1 级问题

#### P1-1 主导航存在死链接

问题描述：

- 侧边栏中存在 `/settings`
- 路由表中没有对应页面定义

影响：

- 用户可进入无效导航
- 产品完成度和可信度下降

整改方向：

- 要么补齐设置页
- 要么在设置页未落地前移除该导航入口

验收标准：

- 所有对外可见导航项都必须映射到可访问页面

#### P1-2 后端缺少企业级校验与异常治理

问题描述：

- 未发现统一的 `@ControllerAdvice` 或同等全局异常治理
- 控制器请求对象未系统性使用 `@Valid`
- Service 中抛出的运行时异常可能直接透传为框架默认错误响应

影响：

- API 错误格式不统一
- 前端难以稳定区分业务错误、校验错误和系统错误
- 运维排障效率下降

根因判断：

- MVP 实现阶段优先关注成功路径
- 错误治理尚未抽象为独立横切能力

整改方向：

- 引入统一错误响应模型
- 增加全局异常处理器
- 为请求 DTO、查询参数、路径参数补充校验

验收标准：

- 校验错误与业务错误统一输出 JSON 结构
- 前端可稳定处理失败状态
- API 不再暴露框架默认异常页面或非标准错误格式

#### P1-3 后端缺少主流平台基础能力

问题描述：

- 当前后端依赖缺少若干主流企业能力，例如安全、校验、健康检查、接口文档、数据库迁移治理

影响：

- 系统难以持续硬化
- 环境切换和数据库演进风险高
- 接入公司基础设施成本偏高

整改方向：

- 增加 `spring-boot-starter-validation`
- 增加 `spring-boot-starter-actuator`
- 根据公司认证方式补齐安全基础层
- 增加 OpenAPI 文档能力
- 引入 Flyway 或 Liquibase 做数据库迁移治理

验收标准：

- 后端具备健康与就绪检查接口
- API 契约可文档化访问
- 数据库变更不再依赖手工漂移控制

#### P1-4 异步执行策略不具备生产级约束

问题描述：

- AI 预热和报告聚合直接使用 `CompletableFuture.*Async()`
- 没有专用线程池、超时策略、并发隔离和熔断策略

影响：

- 共用线程池可能在压力下被耗尽
- LLM 慢请求可能拖累其他请求链路
- 随着流量增加，系统稳定性风险上升

根因判断：

- 为了追求性能引入并发，但没有沉淀为基础设施能力

整改方向：

- 为 AI 和报告任务建立独立 `TaskExecutor`
- 增加超时、重试、熔断和并发隔离
- 将缓存预热与用户请求链路隔离

验收标准：

- 异步任务全部运行在显式线程池上
- 慢速 AI 调用不会挤压核心请求线程
- 超时与失败策略可度量、可验证

### 4.3 P2 级问题

#### P2-1 健康检查深度不足

问题描述：

- 当前健康检查主要返回静态 `UP`
- 没有反映 DB、Redis、AI Provider、缓存等依赖状态

影响：

- 运维无法快速定位依赖故障
- 部署验收不具备足够可信度

整改方向：

- 基于 Actuator 增加健康分组
- 增加 DB、Redis 和关键外部依赖的 readiness 检查

验收标准：

- 健康输出可区分“进程存活”和“依赖就绪”
- 部署验收可以依据健康语义执行

#### P2-2 生产 CORS 默认过宽

问题描述：

- 生产 Compose 默认允许通配符 CORS
- 当前系统又缺少正式认证授权层

影响：

- 安全基线偏弱
- 不利于满足公司内部安全基线

整改方向：

- 去掉生产环境宽松默认值
- 强制生产环境显式配置允许来源
- 在正式推广前补齐认证与授权

验收标准：

- 生产环境必须显式声明允许来源
- 敏感接口具备认证授权规则

#### P2-3 仓库交付体验不完整

问题描述：

- 后端缺少 `mvnw` 等 wrapper
- 本地验证与 CI 一致性较差，依赖开发者本机环境

影响：

- 团队接手成本偏高
- 本地验证与流水线行为不一致

整改方向：

- 增加 Maven Wrapper
- 文档化标准本地验证命令
- 统一本地与 CI 的执行入口

验收标准：

- 干净机器上可以仅依赖 wrapper 运行后端测试
- CI 与本地使用相同入口命令

## 5. 问题优先级矩阵

| 编号 | 等级 | 类别 | 简述 | 主要风险 |
|------|------|------|------|----------|
| P0-1 | Critical | 构建 | 前端构建失败 | 无法交付 |
| P0-2 | Critical | 契约 | AI 同步/串流契约漂移 | 测试失真 |
| P0-3 | Critical | 业务正确性 | 期间值硬编码 | 分析结果错误 |
| P1-1 | High | 体验 | 存在死导航 | 用户路径破损 |
| P1-2 | High | 后端治理 | 无统一异常/校验 | API 不稳定 |
| P1-3 | High | 平台能力 | 缺少安全/健康/迁移/文档 | 无法主流化 |
| P1-4 | High | 稳定性 | 异步执行不可控 | 运行时风险高 |
| P2-1 | Medium | 运维 | 健康检查过浅 | 排障效率低 |
| P2-2 | Medium | 安全 | CORS 默认过宽 | 安全基线不足 |
| P2-3 | Medium | 交付 | 缺少后端 wrapper | 可复现性差 |

## 6. 整改策略

### 6.1 第一阶段：先稳住交付基线

目标：

- 先让构建、测试和核心用户路径稳定

范围：

- 修复前端依赖与构建问题
- 统一 AI 客户端契约
- 去除期间硬编码
- 清理死路由
- 修复 AI 相关测试
- 增加 Maven Wrapper

退出标准：

- 前端构建通过
- 核心前端测试通过
- 后端具备统一可执行验证入口

### 6.2 第二阶段：补齐后端治理底座

目标：

- 将 MVP 后端升级为可治理平台后端

范围：

- 增加请求校验与全局异常处理
- 定义标准错误码与错误响应
- 增加 Actuator 和 OpenAPI
- 引入数据库迁移治理

退出标准：

- API 契约可文档化访问
- 错误返回统一
- 运维健康检查可用

### 6.3 第三阶段：加固运行时稳定性

目标：

- 让 AI 重度链路在真实并发下可控

范围：

- 专用线程池
- 超时、重试、降级、熔断
- 缓存预热与用户请求隔离
- 指标采集：缓存命中率、延迟、失败率

退出标准：

- 异步执行受控
- 模型失败不拖垮主链路
- 运维可观察性能与失败趋势

### 6.4 第四阶段：向公司主流系统对齐

目标：

- 对齐公司工程与安全基线

范围：

- 认证与 RBAC
- 审计日志
- 环境分层与密钥治理
- CI/CD 质量门禁

退出标准：

- 系统可由团队接手，而不是依赖单人维护
- 发布与回滚过程具备规范化步骤

## 7. 建议责任分工

- 架构负责人：负责边界、契约、线程模型和演进路线
- 后端负责人：负责校验、异常治理、健康检查、安全基础层、迁移治理
- 前端负责人：负责 AI 客户端统一、期间状态统一、路由治理、构建修复
- DevOps 负责人：负责 wrapper、流水线、部署验收、环境变量规范
- QA 负责人：负责 AI、驾驶舱、预算偏差、报告等关键链路回归矩阵

## 8. 验收检查清单

- 干净环境可稳定构建
- 所有主导航都有有效页面
- AI 分析使用当前所选期间
- 同步与串流 AI 契约统一且可测试
- 后端具备统一校验与异常处理
- 健康检查能反映关键依赖就绪状态
- 安全与 CORS 默认符合公司基线
- 发布前可由流水线稳定验证系统

## 9. 结论

当前系统有不错的 MVP 基础，但还不能视为公司主流可长期维护系统。最大的短板不是功能多少，而是工程治理能力。建议先按“交付稳定化 -> 平台治理化 -> 运行时加固 -> 企业化推广”这个顺序推进，而不是继续直接堆功能。
